## 3. 実測して分かったこと

### 3-1. LINK_DEG（同一物体の連結幅）に最適値は無かった（08-26）

「なぜ60度なのか」に答えられなかったので、**15〜180度を実際に掃引した**（val 1,358クリップ）。

| ±deg | 至近到達 | 安全抑制 |
| ---: | ---: | ---: |
| 15 | 89.9% | 76.7% |
| 25 | 90.4% | 76.2% |
| **60（現行）** | **95.5%** | **74.5%** |
| 90 | 97.3% | 73.6% |
| 180 | 98.5% | 71.9% |

**結論: 山がない。単調なトレードオフ。60度は最適値ではない。**

含意が2つある。
- **どこに置くかは価値判断**であって、データからは決まらない
- だから**統合指標を作るべきでない**（重みを固定すると、この判断が数字の中に隠れる）→ §5

**判断**: 掃引結果はスライドに載せない。**聞かれたら出す**形にした。

**実装上の罠（記録）**: `_notify_v4_eval.py` は importlib で**自分用に別の v4 を読み込む**ため、
別に `_load` した v4 を patch しても効かない。**掃引は `E.v4` を書き換えること。**

### 3-2. リアルタイムは、測ったら間に合っていた（08-27）

「作り替える前に測る」を実行。IS計算サーバ job3614、A100 MIG 3g。

| | 中央値 | p95 |
| --- | ---: | ---: |
| **GPU バッチ1** | **9.80ms** | 9.88ms |
| GPU バッチ25 | 88.26ms（1窓 3.53ms） | |
| CPU 4スレッド | 89.8ms | 91.0ms |

**実運用は0.1秒ごとに1窓。9.80msは周期の9.8%＝約10倍の余裕。**
**100倍冗長な構成のままで、GPUなら間に合っていた。作り替えは不要だった。**

- 既知の「1判定11.3ms(T4)」は**25窓バッチのスループット**だったと確定
- ⚠️ **CPUだけだと周期の90%**。装着デバイスの計算場所で結論が変わる（未決）
- ⚠️ 重みは読めていない（missing=218/unexpected=225）が、
  **レイテンシは計算グラフだけで決まる**ので時間の値は有効

**教訓: 「冗長だから遅い」は思い込みだった。測る前に作り替えなくてよかった。**

## 5. 決めたこと（理由つき）

| 決定 | 理由 |
| --- | --- |
| **統合指標（SELDスコア相当）を作らない** | 至近到達と安全抑制のトレードオフを潰す。**重みが恣意的**になり、そこが一番議論すべき場所なのに数字に埋まる。掃引で「山がない」と実証済み |
| **閾値を単独で選び直さない** | 上限実験の示す壁は**距離推定**であって閾値ではない。得るものが小さく、**確定評価のやり直し**という代償が大きい。⑦とセットでのみやる |
| **60度の掃引結果をスライドに載せない** | 「なぜ60度か」を自分から開かない。**聞かれたら出す** |
| **まとめスライドは読まない** | 読むと40秒かかる。松澤先生から「それでいい」と言われている |
| **振動デバイスをスコープ外にして発表** | 「工作の知識がないのでなるべくしたくない」という制約。**ただし当日の質疑で「修士を見越した想定か」に「はい」と答え、スコープに入った** |
| **数字を言ったら必ず「実環境は未検証」で閉じる** | 合成データの値を実環境の保証と受け取られないため |
